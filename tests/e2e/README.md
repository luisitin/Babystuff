# End-to-end browser test

Run from the repo root: `node tests/e2e/run.mjs` (optional `--shots <dir>` saves 1x screenshots, `--only 4,7` runs those group numbers). A full run takes about 15 minutes (group 4 alone is about 6, group 14 about 4; `--only` runs just some groups).

- It builds the repo (`node scripts/build.mjs`), then drives Chromium through Playwright against `index.html` (standalone) and `artifact.html` (wrapped in the artifact skeleton, with a mocked `window.claude`: downloads, Gmail connector, `use()` returning null, and no runtime at all).
- Groups: 1 boot and layout, 2 routes, 3 link audit (all programs, including the ones hidden by state and the ones inside "same thing" groups), 4 click-through of every link and button, 5 downloads and copy, 6 backup round trip, 7 Gmail card, 8 fill script on fixture forms (plus-address rules), 9 persistence and privacy, 10 accessibility smoke, 11 Phase G directory, 12 Phase G guided run, tracker and email features, 13 Phase H (prints its own lines 13, 14 and 15), 14 Phase I (prints I1 to I7), 15 Phase J (prints J1 to J10).
- Group 11 covers: best-value order and group headings, ranks, the Truly free, Open to everyone and What you get filters, every card line, the summary numbers, "Show these", the state rule with the Hidden box's Show and Hide buttons (Phase J), "same thing" groups, the due-date plan buttons, saved preferences from older versions, and no sideways scroll at 375px.
- Group 12 covers: the guided run order and default selection, the state rule in the guided list, "Start over" confirmation, tagged addresses in a run, the tracker value line, per-row plus addresses and Gmail links, and the Gmail filters file.
- Expected numbers are never typed in. `lib/model.mjs` loads the real `logic.js`, `email.js` and `fieldmatch.js` in Node and works them out from `data/programs.json`, so the page is compared with the module and the data.
- Dates for the due-date checks are relative to today, so they do not go stale.
- All network is blocked and recorded; the app must make no request of its own. Everything it sees is synthetic: the Gmail mock, the profile and the fixture forms (`lib/fixtures.mjs`). No real site or mailbox is touched.
- Exit code 1 if any check fails; the last line is `N checks, M failed`. The last full run (Phase J build, after the "(shown for now)" wording fix): 4823 checks, 0 failed (896 s, no group repeated). Findings are in `FINDINGS.md`; mutation spot-checks are in `MUTATIONS.md`.
- To test a changed copy of the build without touching the repo, put `index.html` and `artifact.html` in a folder and run `BFF_E2E_BUILD_DIR=<folder> node tests/e2e/run.mjs --only 11,12`. The run then skips the build and uses those files (this is how `MUTATIONS.md` was made).
- Not part of `node --test` or CI: it needs a browser (Playwright is preinstalled locally, not on CI runners). Without Playwright it prints `e2e skipped: Playwright not available` and exits 0.
- `BFF_E2E_SUB=I2,I6 node tests/e2e/run.mjs --only 14` runs only those parts of group 14.
- Files are named without `.test.` on purpose so `node --test` never picks them up.
- Layout: `run.mjs` (runner), `lib/harness.mjs` (reporter, page opener), `lib/model.mjs` (expected answers), `lib/groups-a.mjs` to `groups-f.mjs` (the checks; `groups-e` is Phase H, `groups-f` is Phase I), `lib/mock.mjs` (Gmail and artifact mock), `lib/fixtures.mjs` (synthetic form).

## Seeding storage and the reload guard
- Never seed localStorage from an init script (`addInitScript`, or `open({ init })`) on a file: page. In Chromium a script that touches localStorage before the page runs made the browser empty the whole store of that file: origin on about one load in five, with no app code involved. Pass `open({ profile, seed: { 'bff.prefs.v1': '<json string>' } })` instead: `open()` writes the values with `page.evaluate` on a blank page of the same origin and then opens the app. `seedStore(name, obj)` builds such a map. After the page opens, `open()` checks that every seeded key is still there; pass `seedMayGo: ['bff.xyz.v1']` for a key the app may legitimately remove on load (default: none, so every key is checked; no check needs it today). Or serve the page over http on 127.0.0.1, where the effect was not seen.
- Reload with `reloadAfterWrite(page)` (pause, then reload) or `guardedReload(page)` from `lib/harness.mjs`, not `page.reload()`. Every page records the Storage calls its scripts make (call and key, no values) in `window.__bffRec`. If the store held values before the reload and is completely empty after it, the guard looks at that record. A `clear`, or a `removeItem` of one of those keys, by a script in the page fails the group at once. Only the open document is recorded: what a page does while it is being unloaded (a `pagehide` handler) cannot be seen (a binding call and a `window.name` write made from `pagehide` are lost; measured), so that case also ends as a repeated, then failed, group. If no script did it, the group is run once more from the start and the first attempt's checks are not counted; a second loss fails the group. Any other difference (one key missing or changed while others remain) is not touched by the guard, and the checks after the reload fail on it.
- Checked by mutation on frozen copies of the build: a page that clears localStorage on load fails part I2 at once with "the page itself removed saved data"; a page that removes `bff.prefs.v1` and `bff.tracker.v1` on load fails 8 checks of I2 (folds and notes after a reload).
